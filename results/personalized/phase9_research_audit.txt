## H. METRIC DEFINITION VERIFICATION

### H.1 Validation Metric (during rounds)

**Implementation:** Macro-average of per-client validation ROC-AUC

```
personalized_val_roc_auc = mean([client_1_val_roc_auc, client_2_val_roc_auc, ...])
```

For each trainable client:
1. Load client's personalized model
2. Evaluate on common validation set
3. Compute client-level validation ROC-AUC
4. Average across all trainable clients (simple mean, not sample-weighted)

Standard deviation reported when >1 client.

### H.2 Test Metric (final evaluation)

**Implementation:** Macro-average of per-client test metrics

For each trainable client:
1. Load client's personalized model from best round
2. Evaluate on common test set
3. Compute client-level test metrics
4. Average across all trainable clients (simple mean)

Standard deviation reported when >1 client.

### H.3 Critical Distinction

**Phase 9 test metrics are MACRO-AVERAGED across client personalized models.**

This is DIFFERENT from FedAvg/FedProx, which evaluate a SINGLE pooled global model on the full test set.

**These metrics are NOT directly comparable without metric harmonization.**

## I. PERSONALIZATION IMPLEMENTATION

**Implementation:** Full-model local personalization with FedAvg global aggregation

### What Phase 9 actually does:
1. Maintain one global MLP
2. Each trainable client:
   - Copies the global model
   - Trains locally for 1 epoch on its own data
   - Keeps the resulting model as its personalized model
3. Aggregate all local models using sample-count weighted FedAvg to produce next global model
4. Evaluate each personalized model on validation set
5. Select best round based on average personalized-client validation ROC-AUC
6. After all rounds, evaluate best-round personalized models on test set

### What Phase 9 does NOT do:
- No shared backbone/head split
- No FedPer/FedPerAda algorithm
- No partial aggregation
- Full MLP parameters are updated locally and aggregated globally

### Architecture:
- Standard MLP: Linear(2370) -> ReLU -> Dropout(0.2) -> Linear(128) -> ReLU -> Dropout(0.2) -> Linear(64) -> ReLU -> Dropout(0.2) -> Linear(1)
- Same as Phase 5–8 MLP architecture

## M. PHASE 7/8/9 COMPARISON

**IMPORTANT: Metrics are NOT directly comparable without harmonization.**

### Why not directly comparable:

1. **FedAvg/FedProx**: Evaluate a SINGLE global model on the full test set → pooled metrics
2. **Phase 9**: Evaluate EACH client's personalized model separately, then macro-average → client-level metrics averaged

These are different evaluation methodologies. A fair comparison would require:
- Either evaluating FedAvg/FedProx per-client and averaging
- Or evaluating Phase 9 by pooling all client test predictions

### Available data:

| Condition | Phase 7 FedAvg (pooled) test_roc_auc | Phase 8 FedProx (pooled) test_roc_auc | Phase 9 Personalized (macro) test_roc_auc |

| mild_non_iid | 0.6544 | 0.6545 | 0.6520 |

| strong_non_iid | 0.6256 | 0.6267 | 0.6402 |
| extreme_non_iid | 0.6234 | 0.6220 | 0.6526 |

**Note:** Phase 9 shows higher test ROC-AUC under strong/extreme heterogeneity, but this is comparing macro-averaged personalized metrics against pooled global metrics. Direct comparison is not valid without metric harmonization.

- Best round is early (round 2)
- Validation ROC-AUC declines after round 2
- Test F1 standard deviation is high (0.0869)
- Suggests instability under extreme heterogeneity

### N.4 Personalization Promise
- Personalized models achieve comparable test ROC-AUC to FedAvg/FedProx
- Under strong/extreme heterogeneity, Phase 9 shows higher test ROC-AUC (but note metric difference)
- Personalization appears promising but requires proper comparison

### N.5 Justification for Adaptive Aggregation
- Evidence is suggestive but not conclusive
- Early stopping in strong/extreme conditions suggests potential for adaptive methods
- High variance in extreme non-IID suggests instability
- Recommendation: Proceed with caution, consider adaptive aggregation research
